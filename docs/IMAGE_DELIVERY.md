# Faster catalogue and image delivery

The implementation was updated after pulling backend `005342e` and frontend
`d5b7285`. It extends the existing account-scoped media cache and preserves the
latest onboarding, preview and shopping changes.

## Measured bottlenecks

Before this change, a live Inventory request downloaded all 555 customer-visible
products: 1,902,059 JSON bytes, taking 11.117 seconds in one collected run. Twelve
product images totalled 809,073 bytes; their median request time was 0.863 seconds.
The frontend proxy returned `no-store, no-transform`, overriding any upstream
cache policy. Authenticated image fetches started on component mount, before
native `<img loading="lazy">` could defer the already-downloaded blob.

## Delivery changes

- Inventory requests 24 products using an owner-scoped Firestore cursor, without
  reading full metadata analysis. Filters run on the server; semantic search keeps
  the existing bounded retrieval route. Show more fetches the next page. Sparse
  pages scan a bounded number of records, and legacy full-list clients still work.
- Checkout point-reads only its selected IDs. Price and stock remain rechecked
  when quoting and placing orders. The inventory polling interval is 60 seconds.
- Cards request 384px WebP derivatives; private photo/preview display uses 768px.
  Original files remain available for AI input and downloads. Only these two fixed
  widths are accepted. Existing photographs are resized, not regenerated by AI.
- The private Storage bucket holds versioned derivatives across deployments.
  New product indexing prepares the card thumbnail. Existing catalogue images can
  be prepared with `python -m scripts.warm_catalogue_images --write` using ADC.
- A 32 MiB/256-entry, five-minute instance cache and reused Storage client avoid
  repeated downloads and TLS setup. Authorizations and source-record checks still
  precede a cache hit or conditional 304. Thumbnail transforms are bounded and
  single-flight within each instance. Deletion removes both derivative widths;
  deletion markers prevent late transforms from recreating deleted photos.
- Browser fetches begin only within 300px of the viewport, with at most four image
  downloads at a time. The existing session cache deduplicates and retains loaded
  URLs across screens, isolates accounts and invalidates all variants on deletion.
- Catalogue images allow five-minute **private** browser caching, vary by
  Authorization and support ETags. The Next.js proxy forwards these image headers
  and conditional requests while never caching authenticated bytes on the server.
  Personal photos and previews remain `private, no-store` and session-memory only
  in the browser. Static bundled photos use Next.js responsive image optimization.

## Why Redis was not added

Redis/Memorystore would not reduce the original JSON payload, thumbnail dimensions,
image transfer size or premature browser downloads. The existing Storage bucket
provides durable derivatives; private browser caching and bounded instance memory
cover repeated image requests without an additional always-running service.

For a much larger, geographically distributed catalogue, evaluate a separate public
catalogue-media origin or Cloud CDN with authenticated private bucket delivery.
Customer portraits must remain separately authorized. A load balancer/CDN is not
required for the current fix; no Redis, CDN or GPU resources were provisioned.

References: [Google Cloud Storage caching](https://cloud.google.com/storage/docs/caching),
[Cloud CDN caching](https://docs.cloud.google.com/cdn/docs/caching),
[Next.js image optimization](https://nextjs.org/docs/app/getting-started/images).
