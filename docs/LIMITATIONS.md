# Known limitations and honest capability boundaries

- The deployed demo uses synthetic wardrobe/catalogue facts and licensed illustrative photographs. No retailer POS, commerce, checkout or fulfillment provider is connected. Stock, stores and prices are labeled samples, and cannot be used as a purchasing promise.
- Firebase Google/email authentication is configured. Anonymous demos use isolated seven-day bearer sessions. Signed-in accounts use verified Firebase tokens; private profile/wardrobe data persists separately.
- Google Photos API integration is implemented and its contracts tested with mocks. A dedicated OAuth client, user consent, and live account selection are still required for an end-to-end test.
- Signed-in Gemini extraction, intent and whole-outfit tool assessment were exercised on the deployed GCP services using a licensed sample photo. Google Gemini 2D image editing also produced a real preview from a licensed reference and catalogue shirt in a direct Vertex smoke test. Embedding, Google VTO and Veo adapters have no live output verification here. Provider access, model region and commercial billing are explicit runtime settings. No generated photo/video is fabricated when unavailable. Sample clothing previews use illustrative photographs; product identity, exact fit and preservation of every detail are not guaranteed.
- Uploaded images in credential-free demo mode use manual review. No detection accuracy has been measured. Garment segmentation and image-embedding duplicate grouping are not implemented; current duplicate suggestions use exact evidence-image hashes. Similar colour/category never causes automatic merging.
- Direct uploads retain the validated original and an orientation-corrected resized processing copy in private storage. Google Photos retains the selected 1600px download and a processing copy, not a promise of original full resolution. Dates are evidence of appearance, not a complete wear history.
- Recommendations are bounded, rule-based complete-outfit candidates, with Gemini intent/assessment for configured signed-in accounts. Coverage counts refer only to assessed candidates. Current whole-outfit rules are intentionally simple and do not establish fashion quality, fit, climate suitability or comfort.
- The serving compatibility graph is functional in Firestore/SQLite. BigQuery product projection and SQL schemas/queries are included; personal-graph synchronization, automatic visual catalogue enrichment and online semantic ranking remain integration work. No GQL reservation was created.
- Generated media requires customer review for likeness/garment preservation. No automated similarity/consistency metric has been validated. Motion generation is not interactive AR.
- AR viewer works with an original sample. Personal reconstruction, rigging, garment fitting, expression tracking and pose tracking are not integrated. No GPU resources were provisioned.
- Job cancellation cannot guarantee that an in-flight provider request stops billing. Cloud Tasks can retry transport failures; application retries are explicitly bounded. Distributed transactional outbox delivery and provider-side exactly-once generation are future hardening tasks.
- All expensive customer jobs have daily quotas. Public demo sessions and uploads also have global daily quotas. These are abuse controls, not absolute budget caps. Production needs per-tenant abuse monitoring, retention policies, incident response and a full security review before handling a large customer population.
- Admin forms allow validated JSON editing for variant/stock fields. Rich visual variant editing and bulk per-row import error previews remain future enhancements.
- App navigation uses responsive in-app tabs. Some state, including an active conversation selection, is restored by choosing a saved conversation rather than a URL route.
